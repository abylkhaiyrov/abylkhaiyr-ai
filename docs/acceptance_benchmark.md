# Acceptance Benchmark v1: критерии, зафиксированные до первого запуска

Файл `configs/acceptance/benchmark_v1.json` (33 сценария × RU, EN, KK = 99 запросов), модуль `src/llm/evaluation/acceptance.py`, прогонщик `scripts/run_acceptance.py`. Критерии ниже и содержимое бенчмарка зафиксированы коммитом до получения каких-либо ответов; после просмотра результатов они не меняются (изменение возможно только как новая версия `benchmark_v2` с новым хэшем, результаты v1 при этом не пересчитываются).

## Что проверяется

Проверка идёт через реальный путь пользователя: логин (cookie + CSRF), создание чата REST, сообщения по WebSocket `/api/ws`, ответ реальной загруженной модели. Для каждого запроса сохраняются: запрос, история, фактический prompt (токены `encode_conversation`, декодированные в текст; число токенов сверяется с `input_tokens`, которое сообщил сервер), checkpoint, параметры инференса, ответ, причина завершения, этапы, автоматическая и ручная оценка. HTTP 200 и WebSocket-событие не считаются доказательством правильности.

Причина завершения выводится из события `generation.completed`: `length`, если выдано `max_tokens` токенов, `timeout`, если было событие тайм-аута, иначе `stop` (EOS модели). Сервер не передаёт её явным полем.

Категории: chat, identity, explain, instruction, fact, code, translation, math, multi_turn, context, answerability. Многоходовые сценарии выполняются в одном чате, история включает реальные ответы модели.

## Две независимые оценки

**Автоматическая (детерминированная), где возможен эталон.** Это лексическая и исполняемая проверка, а не семантическая оценка:
- `lexical`: все группы допустимых вариантов присутствуют, запрещённые отсутствуют;
- `number`: ожидаемое число (или слово) присутствует в ответе;
- `count`: слово встречается ровно N раз;
- `code`: код из ответа исполняется в песочнице, первая функция вызывается на фиксированных входах и сравнивается с эталонными выходами;
- `refusal`: ответ содержит маркер недостаточности информации (для неотвечаемых), при необходимости без выдуманного числа.

Лексическая проверка может засчитать неверный ответ, содержащий нужное слово среди прочего, и не засчитать верный перифраз. Она служит ориентиром, но не итогом.

**Ручная оценка (основная).** Рецензент читает каждый ответ вместе с запросом, историей и `key_points` сценария и ставит оценки до сопоставления с автоматикой:
- `relevance` 0/1/2: 0 не по теме или шаблонный отказ без причины, 1 частично по теме, 2 отвечает на заданный вопрос;
- `correctness` 0/1 (или пусто, если неприменимо): 1 только если нет фактической ошибки и затронуты все обязательные `key_points`;
- `completeness` 0/1/2: доля `key_points`;
- `coherence` 0/1/2: 0 бессвязно, 1 искажения слов или повторы, 2 читается как нормальный текст;
- `instruction` 0/1 (если в запросе есть формат или ограничение);
- `refusal` 0/1 (если ответ отказ или должен был быть отказ): 1 уместно;
- `history` 0/1 (многоходовые): 1 использует предыдущие сообщения верно;
- `cause`: одна метка причины ошибки из закрытого списка: `no_knowledge`, `wrong_fact`, `template_refusal`, `irrelevant_template`, `echo_or_repeat`, `copy_wrong_entity`, `context_ignored`, `language_mismatch`, `incoherent`, `format_violation`, `hallucinated_entity`, `incomplete`, `other`.

**Итог «пройден»** (`passed`): `correctness == 1` для сценариев, где она применима; для chat и identity пройден, если `relevance == 2`, `coherence >= 1` и нет ложных утверждений (человек, чужая модель, возможности вне текста).

## Ограничения методики

Один рецензент (ассистент разработки, не носитель казахского и русского языка), поэтому оценки KK предварительные; независимой второй разметки нет. Рецензент знает, какая модель отвечает. Автоматическая проверка запускается отдельно, расхождения с ручной оценкой перечисляются в отчёте. Размер набора 99 (по 33 на язык) даёт интервал около ±8–17 п.п. на язык: различия меньше 10 п.п. не интерпретируются.

## Правило недопущения утечки

Запросы и ответы бенчмарка не входят в обучающие корпуса. Перед каждым обучением проверяется контаминация: нормализованные запросы бенчмарка не должны совпадать с обучающими примерами, а обучающие данные не оптимизируются по ним.
