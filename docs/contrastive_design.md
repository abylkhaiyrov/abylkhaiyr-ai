# Контрастивное дополнение к CausalLMObjective: обоснование и проверка

Задача: обучающий сигнал, который не только повышает вероятность правильного ответа, но и отличает его от содержательно неправильного ответа **в том же контексте**. Реализовано как опциональный блок `train.contrastive` существующего Training Engine (`ContrastiveObjective` рядом с `CausalLMObjective` и `DPOObjective`), второго движка нет. Без блока поведение прежнее.

## Постановка

Для контекста x (запрос, документ, история) задана пара ответов: правильный y⁺ и неправильный y⁻ (программно построенный, см. ниже). Обозначим средний по токенам логарифм правдоподобия на **расходящемся участке**

ℓ(y|x) = (1/|S|) Σ_{t∈S} log p_θ(y_t | x, y_{<t}),

где S — позиции ответа после общего префикса y⁺ и y⁻ (`divergent_masks`). Общий префикс («Столица Германии — …») даёт одинаковые условные распределения в обеих ветвях и в разности взаимно уничтожается; исключение его из S убирает шум и не позволяет «подавлять» шаблонные токены, общие для верного и неверного ответов.

Потеря пары: L_c = −log σ(β(Δ − γ)), Δ = ℓ(y⁺|x) − ℓ(y⁻|x), β > 0 (температура), γ ≥ 0 (требуемый зазор).

Итог на микробатче (суммируется как `loss_sum`, делится тренером на число обучаемых токенов y⁺):

L = Σ CE(y⁺) + λ · N⁺ · mean_pairs(L_c),

то есть после нормировки L/N⁺ = CE_mean + λ · L̄_c. При λ = 0 вторая ветвь не считается, и значение совпадает с `CausalLMObjective` (проверено тестом).

## Математическое обоснование

1. **Градиент.** ∂L_c/∂θ = −β σ(−β(Δ−γ)) (∇ℓ⁺ − ∇ℓ⁻). Увеличивается правдоподобие расходящейся части y⁺ и уменьшается y⁻, с весом σ(−z) ∈ (0,1). Когда зазор достигнут (z ≫ 0), вес → 0: потеря насыщается, в отличие от unlikelihood-потери −log(1−p), которая неограниченно давит вероятность y⁻ и портит общие токены. Для логитов: ∂ℓ⁺/∂z_t = (onehot(y_t) − softmax(z_t))/|S⁺|. Выражение проверено численно (`torch.autograd.gradcheck`, float64) и сравнением с аналитической формулой (`tests/test_contrastive.py`).
2. **Совместимость с MLE.** CE остаётся полным (все токены ответа y⁺), поэтому оптимум по y⁺ не меняется; контрастивный член только перераспределяет массу вероятности внутри расходящегося участка. Градиент не содержит референс-модели (в отличие от DPO), так что вторая копия модели в памяти не нужна: важно для 16–50 млн параметров на MPS.
3. **Что измеряется.** Δ (зазор) и доля пар с Δ > 0 пишутся в метрики (`contrastive/margin`, `contrastive/accuracy`). Рост зазора на обучении не доказывает рост качества ответов: проверка только на независимых запросах (Acceptance Benchmark).
4. **Ограничения.** Δ нормирован по длине расходящегося участка: короткие значения (одно имя, одно число) вносят шумный Δ. Пары без расходящихся токенов (идентичные или префиксные) исключаются из L_c (`valid`).

## Пары (все программные, ответ проверяем по построению)

`llm.data.verified_contrast.contrastive_pairs`: на каждый пример корпуса `verified_v1` одна пара, вид отрицательного ответа записывается в `kind`:
- `wrong_value`: тот же шаблон ответа с чужим значением (другая столица, другое число, чужое имя питомца);
- `other_entity`: правильный ответ на другую сущность того же отношения;
- `other_relation`: ответ про другое отношение (время открытия вместо закрытия, другое намерение);
- `distractor`: в контексте с несколькими сущностями ответ про соседнюю сущность;
- `hallucination`: выдуманное значение при отсутствии информации в документе;
- `unjustified_refusal`: «в тексте не сказано» при наличии ответа в документе.
Пары хранятся в формате `preference/{split}.jsonl` (chosen/rejected с общим контекстом) и читаются существующим `PreferenceLoader`. Негатив строится из той же таблицы знаний, поэтому он содержательно неверен, а не просто перемешан.

## Эксперимент

Один фактор: λ. Обе руки читают одни и те же пары в одном порядке, с одинаковой инициализацией, LR и числом шагов; рука с λ = 0 это чистый SFT на y⁺ тех же пар. Решение по независимому Acceptance Benchmark и по вспомогательным метрикам пар на отложенных сущностях.
