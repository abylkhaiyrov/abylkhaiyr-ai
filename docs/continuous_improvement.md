# Continuous Improvement: контролируемое самообучение без скрытого обновления весов

Реализация: `src/llm/data/feedback_curation.py`, тесты `tests/test_feedback_curation.py`, критерии независимой оценки используют Acceptance Benchmark (`src/llm/evaluation/acceptance.py`). Веса во время диалога не меняются никогда; модель не оценивает собственные ответы.

## Поток

```
Real User Query → Model Response → User Feedback → Error Classification
  → Verified Correction → Curated Dataset → Training Candidate
  → Independent Evaluation → Approval
```

| Этап | Кто и как | Что запрещено |
|---|---|---|
| Capture | `capture()`: только при явном согласии пользователя (`consent=True`), текст сразу очищается от персональных данных и секретов (`scrub`: email, телефон, карта, ИИН, IBAN, токены и ключи, `пароль: …`, URL) | Запись без согласия; хранение исходного текста до очистки; более трёх замен в записи (запись блокируется `too_much_pii`) |
| Classify | Закрытый список причин (`ERROR_CAUSES`, тот же, что в рубрике приёмки). Автоматически только `echo_or_repeat` и `language_mismatch`; остальные ставит рецензент | Самоклассификация моделью |
| Correct | Рецензент или проверяемый источник предлагает правильный ответ; поле `Verification` (вид, проверяющий, доказательство) обязательно; коррекция тоже очищается, при остаточных персональных данных отклоняется | Верификация самой моделью (`verifier` равен checkpoint или начинается с `model:`) |
| Verify | Программные проверки: `arithmetic` (пересчёт выражения из запроса), `knowledge_table` (совпадение с таблицей проверенных ответов); `human_reviewer` принимается как есть, но фиксируется | Пропуск стадий (`classified` → `corrected` → `verified`; нарушение вызывает ошибку) |
| Curate | `curate()`: только `verified` с согласием, без дословных совпадений с Acceptance Benchmark (`protected_keys`), без остаточных персональных данных, противоречивые исправления одного запроса исключаются; запись в `corrections.<версия>.jsonl` с происхождением (идентификатор записи, дата, checkpoint, вид проверки, согласие) и манифестом: версия, родитель, число строк, SHA-256, отклонённые по причинам, классы ошибок, бюджет обучения | Перезапись выпущенной версии (`StoreError`) |
| Training Candidate | Отдельное явное действие через существующий Experiment Runner (спецификация с зафиксированной версией данных и бюджетом шагов); не автоматическое | Обучение во время диалога, обучение «в фоне» |
| Independent Evaluation | Acceptance Benchmark того же SHA, ручная слепая оценка отличающихся ответов, перплексия удержания | Оценка на данных, в которые попали исправления; изменение критериев после просмотра |
| Approval | `approval_decision()`: тот же `benchmark_sha256`, наличие ручной оценки, рост доли пройденных, отсутствие регрессии по языкам (допуск один запрос из 33), перплексия не выше 1,25×; решение дописывается в журнал `record_approval()` (версия данных, бюджет, метрики до и после, подписавший) | Автоматический вывод в Production: `production` остаётся `null` до отдельного решения владельца |

## Что хранится

`studio/feedback/records.jsonl` (append-only, `FeedbackStore`; в Git не входит): последняя запись по `record_id` определяет состояние. Идентификатор записи это хэш очищенных сообщений, ответа и checkpoint, без идентификатора пользователя и чата. Сырые тексты пользователей, не прошедшие очистку, не сохраняются.

## Что не реализовано

- Кнопки «верно/неверно» в интерфейсе и REST-метод приёма обратной связи: сейчас `capture()` вызывается кодом; интеграция с Studio потребует согласия пользователя в профиле и экрана рецензента, это отдельная задача.
- Дополнительные проверяющие (`code_tests`, переводные словари): расширяются добавлением вида в `VerificationKind`.
- Юридическая политика хранения и удаления: код фиксирует согласие и происхождение, но не заменяет политику.
